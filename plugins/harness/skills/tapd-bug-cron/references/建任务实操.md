# 建任务实操记录

真实任务的建任务过程与踩坑记录。配合 `../assets/query-prompt-template.md`（只查）与 `../assets/fix-prompt-template.md`（自动修复）使用。

> 修复流程不在这里 —— 统一由 `/start fixbugs` 执行，见 `skills/start/references/phases/`。

## 零、先选模式

| 用户意图 | 模式 | 提示词模板 | 有无副作用 |
|---|---|---|---|
| 「定时查有没有 bug」「先别动代码」 | 只查 | `query-prompt-template.md` | 无 |
| 「定时修 bug」「查到就修」 | 自动修复 | `fix-prompt-template.md` | 改代码 + 写评论 + 改状态 |
| 没说清 | 只查（默认） | — | 先观察再升级 |

**同一需求只能留一个任务**：只查升级到自动修复时先删旧任务；删除前展示旧任务的 id / cron / prompt 前 50 字确认。

> 旧的「模式 3 手动解冻」已移除：harness 里的等价路径是 `open-questions.json` 待确认
> → 用户答复 → `resolve-question.js` 写入 → 继续推进。单次修复直接用 `/start fixbugs`。


## 一、核心口径（一句话）

### 命名规范：提示词首行必须是需求中文标题

定时任务列表只展示 prompt 开头几十个字。首行写「TAPD 需求关联 Bug 巡检」这类泛称，一屏几个任务全长得一样，认不出对应哪个需求。

```
✅ 【定时任务：轮询需求「【微赞+星享】【惠康】线上优化：忙碌状态的客服，需要支持对用户进行重新发起会话」的关联 Bug（只查不修）】
❌ 【定时任务：查询 TAPD 需求关联 Bug（只查不修）】
```

- 标题照抄需求标题，不改写、不截断 —— 需求前缀（如「【微赞+星享】【惠康】」）往往是区分多个任务的关键
- 模板占位 `{{STORY_TITLE}}`，只查模式 与自动修复模式 都要替换
- 拿不到标题时向用户要，不要用泛称占位

## 一、核心口径（一句话）

```
结果 = get_related_bugs 返回的 bug_id 集合
     ∩ current_owner 命中「处理人」
     ∩ status ∈ {new, reopened}
```

**只调两次**：`get_related_bugs` 拿 id → `get_bug` 带 `id`+`current_owner`+`status` 批量过滤。

| ❌ 已废弃的做法 | 原因 |
|---|---|
| `get_bug(status="new\|reopened")` 全量拉取 | workspace 级，不分需求，实测 85 条里泛词满天飞 |
| `get_bug({"story_id": ...})` | 该字段恒为空，永远 0 条 |
| 标题关键词比对 / 关键词兜底 | 误判率高，用户明确要求禁用 |
| 逐条 `get_bug` 补详情 | N 次调用，浪费；批量查询一次即可 |

## 三、实测踩坑

| # | 坑 | 对策 |
|---|----|------|
| 1 | `get_bug` 的 `owner` 与 `story_id` 恒为空 | 用 `current_owner`；它模糊匹配多人字段，`"黄德鹏;蔡杰鹏;"` 能被 `"蔡杰鹏"` 命中 |
| 2 | 状态传中文「待解决\|重新打开」返回 0 条 | **必须传英文 key**。本项目枚举见下表 |
| 3 | `get_bug` 默认 `limit=10` 截断 `data` | `limit >= N`（传 200）；`count` 仍是真实匹配数，用它判断「是真 0 条还是被截断」 |
| 4 | `fields` 不声明就不返回 | 显式写 `id,title,status,current_owner,created,module,description` |
| 5 | `get_related_bugs` 无 `count` 字段，`limit`/`page` 被忽略 | 数量 = `data.length`；一次返回全量（实测 99 条），不要翻页 |
| 6 | 多需求 / 子需求 | 主+子 id **逗号拼接**在同一字符串里（实测 18+81 → 99 条） |
| 7 | 参数名写驼峰 `storyId` 报错 | 蛇形 `story_id`，且写成 `options={"story_id": "<id>"}` |
| 8 | `workspace_id` 传字符串报 `must be integer` | 传整数 `38260062` |
| 9 | `get_bug` 的 `id` 写顶层报 `additional properties` | `id` 必须放进 `options` |
| 10 | `get_related_bugs` 返回空数组 | TAPD 未建立「需求 ↔ 缺陷」关联，需先去需求详情页关联。**任何 MCP 组合都查不到**，不能拿 workspace 级结果冒充，也不要反复重试 |

### 本项目缺陷状态枚举（2026-11 实测）

| 英文 key | 中文名 | 本 skill 用途 |
|---|---|---|
| `new` | 新 | 查询过滤 |
| `reopened` | 重新打开 | 查询过滤 |
| `in_progress` | 接受/处理 | **B 型验收通过后的回写目标** |
| `assigned` | 已分配 | 不参与 |
| `verified` | 已验证 | 不参与 |
| `resolved` | 已解决 | 不参与（不自动关单） |
| `postponed` | 延期 | 不参与 |
| `rejected` | 已拒绝 | 不参与 |

查询只认 `new` / `reopened`；回写只写 `in_progress`。

**反向校验**（可选）：`get_entity_relations({"relation_type":"bug_story","bug_id":"..."})` 查某缺陷挂在哪个需求下。

## 四、建任务操作要点

具体用哪个工具由当前会话暴露的定时任务能力决定，不写死。执行要点：

| # | 要点 |
|---|------|
| 1 | 创建前先列出当前所有任务 |
| 2 | 替换前向用户展示旧任务的 id、cron、prompt 前 50 字，确认后才删 |
| 3 | 按 `assets/query-prompt-template.md` 或 `assets/fix-prompt-template.md` **整段**生成 prompt，不局部 patch；首行 `{{STORY_TITLE}}` 必须填需求中文标题 |
| 4 | cron 避开 0 分和 30 分：20 分钟用 `7,27,47 * * * *`，30 分钟用 `11,41 * * * *`，60 分钟用 `13 * * * *` |
| 5 | 开启持久化，有效期 30 天 |
| 6 | 同一需求只保留一个任务 |
| 7 | 创建后核对：`.codebuddy/scheduled_tasks.json` 里任务数=1、id / cron / prompt 关键词符合预期 |
| 8 | 告知用户：需求中文标题、任务 ID、持久化位置、有效期、取消方式 |
| 9 | 创建后读回 prompt 前 50 字，确认能一眼看出是哪个需求 |

**任务 id 怎么拿**：不要解析工具返回的文本硬抠，格式未经实测。可靠来源是创建返回值，或直接读 `.codebuddy/scheduled_tasks.json` 的 `tasks[].id`（顶层 `{ "tasks": [] }`，无 `name`/`description` 字段，按 `id` 定位，`expiresAt` 为到期时间戳）。

## 七、运行时：锁与 reopened 判定

> 这两节是整合到 harness 后的新增内容，旧版靠 `.lock` + `todo-list.md` + 指纹，
> 现在统一复用 harness 的单例锁与 `bug-list.json`。

### 7.1 锁：复用 .harness-active，不新建 .lock

| 项 | 说明 |
|---|---|
| 锁文件 | `.codebuddy/plans/.harness-active`（由 `harness-workflow.js` 读写） |
| 内容 | `{ active, storyId, title, mode, activatedAt }` |
| 谁清理 | 只能由 `/harness end` 清理 —— 定时任务无权删除 |
| 定时任务的动作 | **只读**。存在即跳过本轮 |

三种跳过情形：

```
存在 + storyId === 本任务 Story  → 「上一轮仍在执行（Phase N），本轮跳过」
存在 + storyId !== 本任务 Story  → 「其他 Story（X）占用中，本轮跳过」
不存在                            → 正常执行
```

**陈旧标志**（标志在、e2e-state.json 已不存在或已归档）：
提示用户执行 `/end`，本轮结束。**不要自动清理** —— 清理激活状态是状态操作。

**为什么不加超时接管**：旧版的 90 分钟陈旧判定是为了应对进程被强杀。
harness 的标志有对应的 `e2e-state.json` 可交叉验证，判断更可靠，不需要再加时间阈值。

### 7.2 reopened：四态分流

TAPD 只说「现在是 reopened」，不说「是不是我修出来的」。判断依据在 `bug-list.json` 的 `writeback`。

| # | bugs[] 中能否找到 | writeback | TAPD 状态 | 判定 |
|---|---|:---:|---|---|
| A | 否 | — | new / reopened | **新缺陷** |
| B | 是 | 有 | reopened | **真打回 / 疑似误操作**（看评论时间） |
| C | 是 | 无 | new / reopened | **重新分析** |
| D | 是 | 有 | **new** | **已修复待流转，跳过** |

B 类再按评论时间细分：

```
实时 get_comments 取最新评论时间 latestCommentAt
  latestCommentAt >  writeback.commentedAt  → 真打回（修完测试又复现）
  latestCommentAt <= writeback.commentedAt  → 疑似误操作（没人说话，读评论确认）
```

再结合 `writeback.commentKind`：

| commentKind | 说明 | 处置 |
|---|---|---|
| `fixed` | 我们写过「已修复」 | 真打回说明可能没修好：查「修得不全 / 环境未更新」 |
| `to_backend` | 只转给后端，没修过前端 | 后端修完被打回 → 重新分析，**考虑改分类为 frontend** |
| `to_collab` | 只要求联调 | 同上 |
| `manual` | 曾转人工 | 仍需人工判断 |

**为什么不存 `lastCommentAt` 到 bug-list.json**：为单一用途给契约加字段，
会同时增加 schema 骨架体积（有 2KB 成本护栏）。定时任务本来就要读评论判断
「没修好 vs 新问题」，顺手取时间戳即可。

### 7.3 终态后不自动重开

`dispatch` 返回 `terminal` 时只输出待办，不做 `--rollback`：

```
本 Story 主流程已完成（至 Git 提交 + MR）。本轮检测到 N 个新缺陷：...
建议 /harness archive 归档后重新发起。
```

理由：自动重开等于让定时任务决定「何时开启新一轮开发」，是判断权回流。
