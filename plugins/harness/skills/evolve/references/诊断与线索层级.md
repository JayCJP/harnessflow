# 诊断：两层线索与根因归类

Step 2「诊断」的具体做法。目标是区分「新问题 vs 持续问题」，定位 BLOCKER 根因与流程瓶颈。

## 线索分两层，按需下钻

| 层 | 载体 | 回答什么 | 何时用 |
|---|---|---|---|
| 索引层 | `trace.jsonl` | 发生了什么事件、发生几次、在哪个 Phase | 默认入口。先看事件与计数，定位可疑时间段/Phase |
| 载荷层 | `debug.jsonl`（经 `debug-replay.js`） | 事件当时的完整现场：门控 blockers 原文、agentPrompt、hook 拒绝详情、lint 输出 | 索引层看不出「为什么」时下钻，做完整输出对照 |

**铁律：索引层能定位就不读载荷层。** `debug.jsonl` 记录量大，全量展开会淹没上下文。

## 索引层：trace.jsonl

事件类型（来自 `trace-command.js` 旁路采集）：

- `fix_loop` — 触发修复回路
- `gate_decision` — 门控结论（`phase` / `result`）
- `tool_call` — skill / MCP 调用（`skill` / `mcp` 字段）
- `state_change` — 状态字段跃迁

度量脚本 `metrics-aggregator.js` 已经把 trace 聚合成指标（见「指标口径」reference），所以**先看度量 JSON，再按需回 trace 查具体事件**，不要一上来就逐行读原始日志。

## 载荷层：debug-replay.js

```bash
# 全流程时间线（默认单行摘要）
node scripts/audit/debug-replay.js <storyId>

# 只看某 Phase / 某类记录
node scripts/audit/debug-replay.js <storyId> --phase 2 --kind script_output

# 展开完整 payload（门控 blockers 原文 / agentPrompt / hook 拒绝详情）
node scripts/audit/debug-replay.js <storyId> --verbose

# 重建任意历史时刻的状态摘要（索引卡）
node scripts/audit/debug-replay.js <storyId> --card [seq]

# 读归档轮次 / 原始 JSON / 写入文件
node scripts/audit/debug-replay.js <storyId> --round 1
node scripts/audit/debug-replay.js <storyId> --json
node scripts/audit/debug-replay.js <storyId> --verbose --out debug/replay.md
```

记录类型：`script_output` / `method_output` / `hook_decision` / `state_change` / `agent_report`。
工具是**只读**的（除 `--out`），不会写状态文件，可放心在诊断阶段调用。

项目根解析：`CODEBUDDY_PROJECT_DIR` → `CLAUDE_PROJECT_DIR` → cwd，与 `harness-audit.js` 相同。

## 根因归类（BLOCKER / 瓶颈）

按 `harness-audit.js` 的 `cat` 字段归类：

- `state` — `.harness-active` 与 `e2e-state.json` 不一致、dev-pass 无效
- `contract` — acceptance-criteria / open-questions / task-dag / AC-Task 引用问题
- `artifact` — 已越过 Phase 的产出物缺失
- `decl-consume` — story-input 声明了 Figma 但 Phase 1 未产出 frame 清单
- `dev-pass` — dev-pass 相关

区分新/持续问题：对比上一次 `/evolve` 报告，同类 `cat` 反复出现即为持续问题，优先治理（对应 `evolutionLevel: pattern/instinct`）。
