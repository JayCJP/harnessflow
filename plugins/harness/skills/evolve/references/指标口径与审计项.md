# 指标口径与 fixbugs 审计项

## Step 0 体检：harness-audit.js

```bash
node scripts/audit/harness-audit.js --json     # /evolve 用这个
node scripts/audit/harness-audit.js            # 人读报告
node scripts/audit/harness-audit.js --fix      # 仅清理过期 dev-pass（不改状态/契约）
```

输出 `{ summary, issues, warnings, fixed }`；`issues` 是 BLOCKER，`warnings` 是 WARNING。
有 BLOCKER 时 exit 1。审计项见「诊断与线索层级」reference 的 `cat` 归类。

注意：`open-questions` 的「待用户确认」是流程正常中间态，不告警；只有「缺建议稿（resolution 为空）」才告警。

## Step 1 度量：metrics-aggregator.js

```bash
node scripts/audit/metrics-aggregator.js --json           # /evolve 用这个（不写全局库）
node scripts/audit/metrics-aggregator.js --global-stats   # 看全局洞察库摘要
node scripts/audit/metrics-aggregator.js                  # 聚合 + 合并到全局经验库
```

`/evolve` 必须带 `--json`（只读，不污染全局经验库）。默认模式会 `mergeInsightsToGlobal`。

### 现行指标口径（以代码为准）

| 指标 | 口径 |
|---|---|
| `phaseDurations` | 每 Phase 的 startedAt→completedAt（或 rolledBackAt），avg/median/max |
| `gateFirstTryRate` | 门控一次通过（pass 且无 warnings）占全部推进的比例 |
| `fixLoopTriggerRate` | **Story 级**：触发过有效 fix-loop 的 Story / 到达 Phase 3 审查的 Story |
| `fixLoopSuccessRate` | **Story 级**：首轮修复成功的 Story / 触发过 fix-loop 的 Story |
| `fixLoopEventCount` | 有效 fix-loop 事件数（扣除「全部 issue 均 skipped、无 status=fixed」的空转轮次） |
| `blockerCount` | gateValidationResults 里 blockers 数量之和 |
| `storyCompletionRate` | `status === 'completed'` 的 Story 占比（不看 phase>=6 旧口径） |
| `resourceUsage` | tool_call 事件统计：skill / kb（kb-query\|graphify）/ mcp 调用数 |

阈值：Phase 平均耗时 >20min、门控一次通过率 <80%、fix-loop 触发率 >40%、成功率 <80%。
洞察按 `targetPhase` 定向注入，规则见 `generateInsights()`。

### 两个口径陷阱

1. **空项目噪声**：`storyCount: 0` 时 `gateFirstTryRate`/`fixLoopSuccessRate` 仍输出 1（满分默认），无诊断意义——读到 0 Story 直接跳过度量结论。
2. **kb-not-consumed 规则**：`kbCalls === 0 && skillCalls > 0` 会告警。但 graphify CLI 不可用时 Agent 会用原生 Grep/Read 替代，此时该规则是误报，诊断时需人工排除。

## fixbugs 模式的审计边界（已知盲区）

当前 `harness-audit.js` / `metrics-aggregator.js` **不含 fixbugs 感知**（全仓无 `fixbugs`/`bug-list`/`mode` 字样）。诊断 fixbugs Story 时，evolve 的三件套会把它当普通 run，以下 fixbugs 专有契约**不在自动审计范围**，需人工核对：

- `bug-list.json`（唯一结构化缺陷清单信源）是否存在、schema 是否合规 → `schemas/bug-list.schema.json`
- 缺陷是否分诊（门控 `checkBugList` / `checkBugListEmpty` / 未分诊 BLOCKER）
- 前端缺陷是否都排进了 `task-dag.json`（门控 `checkFrontendBugScheduled`）
- TAPD 回写凭证是否产出（`ff6ff1d` 起改为写协议契约）
- 「TAPD 查无符合缺陷」是**合法终态**（有专门的 blocker 判定），不是空清单错误

判断 Story 模式看 `e2e-state.json` 的 `mode` 字段（`run` / `fixbugs`）。

## Step 3 治疗：提案目标与 evolutionLevel

目标文件：`agents/*.md` / `policy.js` / `advance-phase.js` / `schemas/` / `scripts/lib/*`。

`evolutionLevel`：
- `lesson` — 单次问题，写入经验库失败模式
- `pattern` — 跨 Story 复现，提炼为通用规则
- `instinct` — 高置信、低风险，自动注入 Agent prompt

⚠️ 提案若涉及「同一事实多处实现」，按仓库铁律收敛到单一信源、删副本、不留 fallback（参考 `phases.js` 的 PHASE_ARTIFACTS / `scope.js` 的既有收敛案例）。
