# 淘宝主播 Agent 的 Harness 工程实战 — 深度研读笔记

> 原文来源：阿里技术团队微信公众号（2026年6月发布）  
> 题目：《更可靠的主播助理：淘宝主播Agent的Harness工程实战》  
> 本文是一篇面向工程落地的方法论文章，核心问题是：**如何将概率性的、会漂移的大模型能力，转化为直播场景下可用、可控、可演化的工业级产品？**

---

## 一、为什么直播是 Agent 工程的终极压力测试场

直播场景有四重极端需求，任何一层出问题都是真金白银的损失：

### 1.1 操作即时生效且不可逆

Agent 发出的指令（改价、切品、开播、推送优惠券）直接作用于生产系统，没有"撤消"按钮。单次错误可能导致**超百万元的经济损失**。

### 1.2 主播注意力极度稀缺

主播在镜头前需要同时：讲解商品、看弹幕互动、盯实时数据、控场调度。不可能逐条核验 Agent 的每个动作。**安全边界必须由工程兜底，而非依赖人工复核。**

### 1.3 多话题高频交织（上下文漂移）

单场直播中，以下话题交替出现，且可能出现在同一轮对话中：
- 播前准备：商品排序、价格核对、素材检查
- 播中控场：实时数据解读、节奏建议、突发应对
- 播后复盘：整场数据汇总、问题回溯

**上下文极易污染和漂移，需要工程手段持续治理。**

### 1.4 长程、可中断、需恢复

直播动辄 4-6 小时，主播经常跨设备切换（手机 → 平板 → PC）。Agent 必须能在任意时刻中断，并在恢复时精确续连——不能"失忆"。

---

## 二、Harness 六元组：工程化的分析框架

文章将 Agent 的工程骨架抽象为 **Harness = (E, T, C, S, L, V)** 六个核心模块，每个模块对抗一类特定问题：

| 模块 | 职责 | 对抗的问题 |
|------|------|-----------|
| **E**xecution Loop | 驱动"思考→行动→观察"主循环 | 失控、死循环、无限重试、跑飞 |
| **T**ool Registry | 定义工具能力边界及错误反馈 | 能力边界模糊、参数非法、错误无法恢复 |
| **C**ontext Manager | 维护上下文质量与体积 | 上下文膨胀、注意力漂移、信息退化 |
| **S**tate Store | 持久化运行状态，支持中断恢复 | 长任务中断丢状态、不可回放 |
| **L**ifecycle Hooks | 在关键时机插入强规则拦截/注入/记录 | 纯靠 Prompt 不可控的横切关注点 |
| **V**aluation Interface | 让质量可量化、可追踪 | 质量不可度量、问题不可回溯 |

### 核心设计哲学

> **"业务方专注写 Skill，框架层兜住所有安全、状态、上下文与可观测的脏活。"**

将"不变的"工程能力（执行循环、上下文治理、安全防护、状态持久化）留在框架层，把"会变的"业务逻辑以 Skill 形式声明式注册，实现快速迭代而不牺牲可靠性。

## 三、上下文工程：对抗概率性遗忘的系统设计

这是全文最精彩的部分之一。与传统"把一切都塞进 prompt"的做法不同，淘宝团队设计了多层上下文治理体系：

### 3.1 分层压缩（三级策略）

当上下文 Token 超出阈值时，不简单地截断，而是分级处理：

```
第一级：压缩历史工具调用（Tool Call / Tool Result）
    — 将结构化的工具调用记录压缩为 key-value 摘要
    — 保留"做了什么 + 结果是什么"，丢弃原始 payload

第二级：压缩历史对话轮次
    — 将多轮对话压为一个自然语言摘要
    — 按直播阶段打标签（pre-live / on-live / post-live）

第三级：压缩当前消息
    — 在极端情况下对当前轮次做轻量压缩
    — 保留关键指令，丢弃冗余修饰
```

### 3.2 Reducer 模式（借鉴前端状态管理）

这是全文最独特的设计思路之一：

- **LLM 只负责决策**：产生 Action（意图 + 参数）
- **Reducer（纯函数）负责确定性状态变更**：将 Action 作用于当前 State，产生新 State
- **每轮推理前**：将结构化 State 通过 `system-hint` 注入上下文

这样做的效果：
- LLM 不需要记住状态细节（因为它不可靠）
- 状态变更可追溯、可回放
- 上下文体积可控——State 是结构化数据，不是自然语言

### 3.3 大上下文卸载

大体量内容（商品详情、历史对话全文、素材库）不常驻上下文，而是：
- 卸载到 OSS/Tair 等外部存储
- 上下文中只保留 `fileKey` 和内容预览
- 按需读取、按需注入

## 四、Tool Registry（工具注册中心）：让模型"会用工具"而不是"乱用工具"

### 4.1 三层强化设计

**第一层：能力边界声明**

每个 Skill 注册时必须声明：
- 能力范围（支持什么、不支持什么）
- 参数 Schema（JSON Schema 约束）
- 风险等级（无副作用 / 有副作用 / 高危操作）

Agent 调用前框架自动校验：请求是否在能力范围内？参数是否合法？

**第二层：Schema 强约束 + 幂等设计**

- 所有工具签名通过 JSON Schema 约束，杜绝非法参数
- 所有副作用操作携带**幂等键（UUID）**
- 框架层维护幂等键缓存，**杜绝"双改价""双切品"等灾难性重复操作**

**第三层：结构化错误码 + 自动修复**

| 错误码段 | 类型 | 框架行为 |
|---------|------|---------|
| `3xxx` | 业务异常 | 换策略重试 |
| `4xxx` | 参数异常 | 框架自动修复后重试 1 次 |
| `5xxx` | 系统异常 | 最多重试 3 次，指数退避 |
| `9xxx` | 不可恢复 | 不重试，立即通知主播 |

### 4.2 Skill 发布流程：像发布代码一样发布技能

1. 开发者编写 Skill（代码 + Schema + 能力声明）
2. 提交到 **GitLab** 进行 Code Review
3. 通过**预检平台**校验（验证是否满足定位声明）
4. **灰度发布**逐步上线
5. 生产环境监控 + 回滚机制

## 五、PlanEngine：用 DAG 全局规划替代 ReAct 单步推理

### 5.1 为什么需要 PlanEngine

传统 ReAct 模式（每一步推理→动作→观察→再推理）在直播场景下有致命缺陷：
- 复合指令效率低（"开播提案 → 创建直播间 → 同步商品 → 生成手卡 → 开启智能标题" 需要大量迭代）
- 逐步推理容易顾此失彼
- 失败后难以恢复

### 5.2 PlanEngine 五大设计目标

1. **可恢复**：三层 Checkpoint（每轮对话结束 / 每个子任务完成 / 计划变更）
2. **可观测**：Plan → SubTask → Tool Call 三级状态可视化，全链路 TraceID 追踪
3. **执行效率**：DAG 中无依赖的子任务并行调度
4. **执行成功率**：全局最优规划 + 增量 Replan + Token 额度控制
5. **降低上下文漂移**：执行进度外挂（不占 Context Window），SubAgent 上下文隔离

### 5.3 增量 Replan

子任务失败时，**只重规划受影响的节点**，不推翻整个计划。这是 PlanEngine 比 ReAct 效率高的核心原因之一。

### 5.4 效果对比

| 指标 | PlanEngine | 传统 ReAct |
|------|-----------|------------|
| 执行成功率 | **0.847** | 0.737 |
| 子任务覆盖率 | **0.976** | 0.883 |
| 工具执行冗余率 | **0.587** | 0.727 |
| 平均迭代轮次 | **5.44** | 8.02 |

## 六、三层记忆体系：让 Agent "越用越懂主播"

### 6.1 记忆分层

| 层级 | 性质 | 来源 | 典型内容 |
|------|------|------|---------|
| **L1 会话记忆** | 主观 | 主播口头声明 | 偏好、约束、反馈、风格要求（"我不喜欢在讲品时被打断"） |
| **L2 事实记忆** | 客观可查 | 系统数据 | SKU 货盘、价格、风控词、本场目标、库存 |
| **L3 行为记忆** | 客观需聚合 | 实际行为追踪 | 主播操作模式、互动习惯、粉丝画像演变 |

### 6.2 记忆对账机制（最精彩的设计）

> 主播"说的"和"做的"不一定一致。

系统通过 **Decision Trace Log** 记录决策全链路，持续将 L1（主观声明）与 L3（实际行为）做对账：

- **声明与行为一致** → 该规则 `confidence` 提升
- **声明与行为矛盾累计 ≥ 3 次** → Agent 主动提示主播更新偏好（"您之前说 X，但实际您做了 Y，需要我更新吗？"）

### 6.3 信任度自进化算法

不是简单的"采纳+1，拒绝-1"，而是**非对称的、基于结果的**信任度更新：

| 场景 | 信任分变化 | 设计意图 |
|------|-----------|---------|
| 主播采纳 + 效果好 | `+0.05` | 正循环激励 |
| 主播采纳 + 效果差 | **`-0.10`**（非对称惩罚） | 错误建议被采信是最大失败 |
| 主播拒绝 + 事后证明 Agent 对 | `+0.03` | 建立长期认知 |
| 主播拒绝 + 事后证明主播对 | `-0.05` | 判断失误需要修正 |

### 6.4 输出形态随信任分自适应

| trust_score | 输出形态 |
|-------------|---------|
| ≥ 0.7 | 直接给 **Recommend**（快速通道） |
| 0.4 ~ 0.7 | 给 **Evidence + 弱参考**（辅助决策） |
| < 0.4 | 只给 **Evidence**（不主动建议） |

### 6.5 遗忘机制

多因子加权衰减，保证记忆库长期不失控：
- 场景相关性（与当前直播的关联度）
- 信息新鲜度（距今时间）
- 时间衰减（指数衰减曲线）
- 可信度因子（高置信度记忆衰减更慢）

## 七、五层纵深安全防御体系

直播场景容错率极低，单一防护层不够——需要纵深。

### 第一层：Prompt 边界硬编码

- 系统提示词硬编码 Agent 能力边界与行为禁区
- 配合 Skill 定位声明和上线前预校验
- 是"最后一道意图防线"，但不可依赖

### 第二层：Schema 强约束

- JSON Schema 约束所有工具签名
- 幂等键（UUID）机制，框架层去重
- 杜绝"双切品""双改价"等灾难性重复执行

### 第三层：Approval 审批分层

这是平衡**安全**与**流畅**的核心设计——不是所有操作都阻塞主播：

| 风险等级 | 触发条件 | 策略 |
|---------|----------|------|
| **auto** | 无副作用操作（查数据、读状态） | 系统直接放行 |
| **soft-gate** | 有副作用但在安全阈值内 | 会话中提示但不阻塞 |
| **hard-gate** | 品类操作、批量操作 | **阻塞等待主播二次确认** |
| **block** | 触发平台红线规则 | 直接拒绝并告警 |

### 第四层：工具执行验证层

- 业务方控制，执行时做业务规则校验
- 返回结构化错误码（3xxx / 4xxx / 5xxx / 9xxx）
- 框架根据错误码类别采取不同恢复策略

### 第五层：执行审计记录

所有工具调用的完整生命周期记录，服务于：
- **实时监控告警**（异常模式即时发现）
- **事后复盘**（按时间线完整回放）
- **模型优化**（积累高质量 fine-tuning 数据集）
- **争议处理**（不可篡改的证据链）

### 额外防护：沙箱隔离执行

对代码类执行统一套沙箱：
- 非特权用户运行
- 根文件系统只读
- CPU 限额 50%，进程上限 64
- 网络默认禁止出站，按白名单放行
- 系统调用白名单收敛

### 异常降级策略

| 异常类型 | 检测方式 | 降级策略 |
|---------|---------|---------|
| 幻觉输出 | 交叉验证 | 拦截并重新推理 |
| 死循环 | 相同工具调用 ≥ 3 次 | 强制中断 |
| 响应超时 | 超时计时器 | 返回预设兜底话术 |

## 八、Lifecycle Hooks：在关键时机注入强规则

不改写模型推理循环，只在关键节点做 **拦截 / 注入 / 记录**：

| Hook 时机 | 作用 |
|-----------|------|
| **PreReasoning** | 注入最新 State 和场景记忆到 system prompt |
| **PreToolCall** | 安全拦截：校验能力边界、幂等键、风险等级 |
| **PostToolCall** | 结果校验 + Reducer 状态更新 |
| **PostReasoning** | 幻觉检测（输出是否与事实一致？） |
| **OnSessionEnd** | 记忆回写（沉淀本场经验） |
| **OnLiveEnd** | 整场数据归档 + 信任度更新 |

---

## 九、存储架构：逻辑统一、物理分治

不是"一个数据库存所有"，而是按数据特征分治：

| 存储 | 数据类型 | 选择原因 |
|------|---------|---------|
| **MySQL** | 会话数据、Checkpoint | 强一致、点查高效、事务支持 |
| **Hologres** | 记忆数据（L1/L2/L3） | 向量 + 全文 + 标量混合检索 |
| **GitLab** | Skill 代码 | 版本管理、Code Review、灰度发布 |
| **OSS/Tair** | 大上下文卸载 | 大体量文件存储，按需加载 |

## 十一、Execution Loop（执行循环）

采用**状态机模式**实现主执行流程：

```
INIT → PROCESSING → COMPLETED / ERROR
         ↑              |
         └── 重试/恢复 ──┘
```

内建保护机制：
- 最大重试次数限制
- 指数退避策略
- 熔断机制（连续失败自动降级）

## 十三、核心启示与思考

### 13.1 工程骨架决定 Agent 的上限

> "模型能力是概率性的、会漂移的——真正让 Agent 可靠的是包裹模型的工程化'骨架'。"

这是全文最核心的论断。不是让模型变强，而是**用工程手段让模型变可靠**。类比：河道（流程）、闸门（审批）、护栏（校验）确保水流可控，而不是指望每一滴水都"听话"。

### 13.2 分层解耦是关键

框架层与业务层彻底分离：
- 框架层：执行循环、安全、状态、上下文、可观测 —— **不变**
- 业务层：以 Skill 形式声明式注册 —— **快速迭代**

这解决了"安全 vs 敏捷"的矛盾——业务方不碰框架代码，框架的可靠性不会因业务迭代而降级。

### 13.3 记忆不是简单的 RAG

三层记忆 + 对账机制 + 信任度自进化的设计，把记忆从"静态知识库"变成了**动态演化的认知系统**。尤其是 L1 vs L3 的对账——承认主播说的和做的不一致，并以此驱动偏好更新——是非常深刻的工程洞察。

### 13.4 安全是纵深防御，不是单点防护

五层防线（Prompt → Schema → Approval → 执行验证 → 审计）让每层失效时都有下一层兜底。Approval 分层（auto/soft-gate/hard-gate/block）巧妙平衡了安全与流畅——不是所有操作都需要阻塞主播。

### 13.5 PlanEngine 是 ReAct 的必然进化方向

DAG 全局规划 + 增量 Replan + 并行调度，本质上是把"下一步做什么"从 LLM 手里拿过来、交给确定性更强的规划引擎。这在多步骤复合任务中带来了 ~15pp 的成功率提升，是一个明确的架构演进信号。

---

> **一句话总结**：淘宝主播 Agent 的 Harness 工程实战，本质上是一次**将概率性 AI 能力转化为确定性工程产品的系统性实践**——用六元组划清工程边界、用五层纵深防御扛住极端场景、用三层记忆实现"越用越懂主播"、用 DAG 全局规划替代单步推理，最终把 Demo 变成了真正可规模化落地的工业级产品。
